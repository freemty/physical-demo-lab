# 仿真展示层与已验证物理分离

依据 [送餐样板报告](../../../reports/demo006-restaurant-showcase.md)，2026-09-06。

- 物理通过不等于展示完成。颜色、物体可辨识度、空间细节与镜头应单独验收。
  用户本次要求彩色、生动的餐厅；不能将网页默认黑白品牌规范套到场景里。
- 保留控制器/验证器原字节，以单独运行入口扩展视觉层。添加布景不附加碰撞或刚体 API，
  保留物理材质的专用绑定；运行前保存并比较原物理 prim 的属性、几何、变换、驱动和材质关系。
  这套守卫用于本次受控扩展，不声称是任意 USD 修改的全面等价证明。
- 不只看颜色配置值。首轮有材质和布景后室内仍暗；后续把主光从被后墙遮挡的一侧
  改到开放前侧并补环境光，实际画面更清楚。这是组合修改，不是单参数消融。
- 显式平滑网格改善本次杯盘基础圆柱的多边形外观。包装印字需位于色带表面外侧，
  第一版便当字样因几何深度被遮住，调整薄层位置后在最终渲染可读。
- 相机刚切换时的 RGB 读回可能仍属于旧视角。本次新视角保持 12 步后再取缩略图；
  不为等画面额外推进物理，否则会破坏控制步/仿真时钟对应关系。
- 在本次 seed 0，最终外观版与原基线全部 2974 个物理帧精确相等，同时通过原成功谓词。
  此实测比只声称“不改控制器”更强，但不能直接泛化为任意新视觉资产都会保持轨迹一致。

新外壳、杯盘、植物和背景家具仅服务展示；不得把未建模的碰撞、液体或操作语义写成新能力。
原失败和旧视频保留，样板另存。推广到其他任务前，应继续检查操作遮挡、完整镜头与各自物理契约。

## 后续任务的展示验收清单

以下是基于本次经验整理的复用步骤，不表示其他 demo 已执行这些检查。

1. 先声明物理验收范围和展示目标。保留原控制器、碰撞、质量和驱动；
   装饰物是否可交互必须明说，不能靠外观暗示新能力。
2. 查看实际渲染：颜色是否被冲淡或压暗、包装是否可辨、印字是否被表层遮挡、
   机器人和关键接触区域是否入镜。具体灯光数值和“等待 12 步”不是跨场景保证。
3. 检查操作、移动和终态镜头；核对相机事件对应的物理阶段与实际画面。
   完整解码只证明媒体可读；报告另列实际查看的画面或时间段，不声称逐帧人工验收。
4. 同初态复跑并重放原物理检查，同时核对前后物理属性和基线逐帧比较结果。
   如有差异，先解释或修复，不能直接沿用“只改外观，所以轨迹不变”。
5. 保留旧版、失败尝试和新视频独立目录；更新报告、经验和项目 TODO 后再推广到下一项。

## 当前审计器的已知缺口

2026-09-06 按源码核对：[audit_showcase_task.py](../../../scripts/audit_showcase_task.py)
的 `audit_showcase()` 会输出 `baseline_trajectory_comparison`，但其 `success`
表达式未包含 `all_physical_fields_exact`。因此退出 0 或顶层 `success: true`
不能单独证明基线一致，必须另外检查比较结果非空、总帧数大于零、匹配数等于总帧数、
且 `all_physical_fields_exact: true`。还应确保所有镜头事件都在轨迹中找到对应帧，
而不只是对碰巧匹配的帧检查阶段。

当前 [送餐审计记录](../../../reports/demo006-showcase-audit.json) 的比较结果为
2974/2974 且该字段为真，所以本次样板的一致性结论仍有独立字段支持。
