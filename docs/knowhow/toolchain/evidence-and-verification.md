# 轨迹、验证器与可复用边界

依据：[首次验证报告](../../../reports/bootstrap-validation.md)、
[独立审计](../../../reports/audit-final.json) 和当前执行源码。验证于 2026-09-06。

现有证据链为：启动命令与 GPU 快照 → 启动前源码快照 → USD 场景与初始条件 →
每个控制物理步的状态/目标 → 事件 → 最终物理判定 → 视频/图像 → 进程返回码。
原始文件放 Data1，仓库保留源程序、紧凑结果和指向原始证据的报告。

- 不只记录 Git commit。运行时 `source/` 与 SHA-256 才能覆盖未提交修改；
  失败若发生在启动阶段，也应尽量留下实际源码和调用参数。
- `trajectory.jsonl` 保留每步控制与状态，`events.jsonl` 便于定位状态切换；
  `audit_runs.py` 复核源码快照、编号/时间连续性与最终物理检查。
- 当前审计器不验证进程退出码，且写死三物体流水线场景；`evaluate.py` 也调用流水线入口。
  不要把它们直接当作通用任务评测器。新任务先定义自己的成功条件，再适配执行与审计。
- 当前 `single_controller_hash` 字段实际比较完整 demo 源文件。仅退出代码改变也会变成
  false；报告必须解释版本变化，不能把重跑后的集合写成固定版本首轮成功率。
- 视频是实际渲染，但外观不能替代物理判定。需查看关键抓取、搬运、释放和最终状态；
  新任务若没有可见接触、隐式约束或使用已知状态，应在报告明确说明。

可以复用：Data1 目录约定、新输出目录保护、源码/调用快照、逐步记录和非零失败码契约。
需要逐任务设计：机器人/资产、控制器、初始状态分布、接触约束、成功谓词和负向测试。
10 个种子的流水线结果不证明收银、齿轮、双臂或灵巧手任务会同样成功。
