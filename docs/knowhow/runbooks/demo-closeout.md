# 每个 demo 的完成与经验写回

本流程落实用户 2026-09-06 的项目约定：每次做完，将可复用经验更新到项目文档，
再推进下一项。记录只写这个仓库；不自动同步到个人 wiki、不启动后台任务。

## 开始前

从 `docs/demos.json` 选当前一项并标记 `in_progress`。先读项目地图及相关 knowhow，
复用已验证环境和接口。给该项建立 `docs/specs/<id>-<name>.md`：参考材料实际覆盖范围、
任务输入输出、机器人与资产、允许的观测/控制、随机化范围、物理成功条件、负向用例、
运行预算与停止条件。对未获得的原视频、源码或物理语义明确标缺口。

## 做完一个可交付阶段后

1. 核对实际运行证据：源码/调用、状态轨迹、物理 verifier、进程返回码、关键媒体画面。
   失败与重跑使用各自目录；先区分物理故障、控制故障、运行时故障和未完成。
2. 使用 LabMate `update-docs` 更新 `reports/<id>-<milestone>.md`。
   报告包括验证日期、任务范围、确切版本、参数和原始路径、全部重要失败、修复、
   重跑情况、最终结果及没有验证的边界。部分完成就如实记录，不强行写成成功。
3. 把下一项能复用的经验补到 `docs/knowhow/` 的相关条目；包括症状、已观察原因或
   明确标注的假设、实际修改、成功/负向证据、适用边界。优先更新既有条目；
   没有新经验就在报告说明复用了哪些条目，不杜撰新发现。
4. 有稳定的新架构/接口/坑点时，使用 LabMate `update-project-skill` 更新简短地图、
   两侧相同的 CHANGELOG 和本机 `.pipeline-state.json` 的 `skill_updated_at`。
   原始日志不能复制进 project-skill；Codex/Claude 两侧内容保持一致。
5. 更新 `docs/README.md`、`docs/demos.json` 和根 `CHANGELOG.md`。
   只有达到本次明确的 scope 才标记 `complete`；报告、经验与证据文件不能缺失。
   记录所有影响该项行为的入口/控制/验证文件的 SHA-256；源码后来变化会使原收尾记录过期。
6. 验证后再交付并推进下一项：

   ```bash
   python3 scripts/check_closeout.py --demo demo001
   bash scripts/check_project.sh
   ```

将示例 ID 换成实际项。没有报告、经验、已知限制，或者实现文件指纹变化，
完成检查应失败。源码只改了清理或日志也需要解释影响和补做相应验证，不能仅刷新哈希消除提示。
运行失败时先写回已知证据，状态保留 `in_progress` 或 `blocked`；不要把失败条目抹掉。

## 机制的能力边界

`AGENTS.md` / `CLAUDE.md` 规定了执行者的收尾责任，`check_closeout.py` 检查记录完整性
和实现指纹，不能自动判断文字真假或自动生成正确经验。它不是物理 verifier，也不是
已安装的 Stop hook、定时任务或不可绕过的分支保护。每次实际执行者都必须运行它并审阅证据。
服务器没有 LabMate 插件时，仍可按这份仓库内流程直接维护文档；不以可选插件安装为阻塞条件。
